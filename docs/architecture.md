# Как GPS-время попадает в метку LoRa-пакета

## Три независимые шкалы времени

1. **Счётчик концентратора** — 32-битный счётчик SX1303 с шагом 1 мкс,
   переполняется примерно каждые 71 минуту. Именно он попадает в поле `tmst`
   и используется для расчёта окна RX1/RX2 при передаче вниз.
2. **Системные часы Linux** — обслуживаются chrony. К меткам пакетов отношения
   не имеют; нужны для логов, TLS и поля `time`, когда GPS потерян.
3. **Шкала GPS** — приходит двумя путями: «грубо» (UTC с точностью до секунды)
   из NMEA-сообщений RMC/GGA и «точно» (момент начала секунды) из импульса PPS.

## Сопоставление шкал

Аппаратно импульс PPS заведён на вход концентратора. По его фронту SX1303
защёлкивает своё текущее значение счётчика. Поток GPS в пакет-форвардере
(`thread_gps` / `thread_valid` в `lora_pkt_fwd.c`) раз в секунду:

1. читает из NMEA, какой именно UTC-секунде соответствовал последний PPS;
2. вызывает `lgw_get_trigcnt()` — какое значение счётчика было защёлкнуто;
3. `lgw_gps_sync()` строит линейную модель `счётчик → время` с оценкой
   дрейфа кварца (`xtal_correct`).

После этого для любого принятого пакета его `tmst` пересчитывается в UTC и в
GPS-время: в JSON-кадре появляются `time` и `tmms`. Если модель устарела
(нет PPS или нет NMEA дольше нескольких секунд), форвардер помечает опорную
точку невалидной и перестаёт добавлять `tmms`.

Отсюда практические следствия:

* **`tmst` есть всегда**, даже без антенны GNSS;
* **`tmms`/`time` требуют обеих составляющих** — и NMEA, и PPS на концентраторе;
* **точность системных часов Linux ни на что тут не влияет.** PPS на GPIO
  Raspberry Pi (`/dev/pps0`) — отдельная, необязательная история для chrony.

## Тонкая метка времени SX1303 (`ftime`)

SX1302 и SX1303 отличаются наличием у последнего блока тонких меток времени.
Он измеряет момент прихода преамбулы с разрешением порядка наносекунд
относительно того же счётчика — это то, на чём строится TDOA-геолокация
оконечных устройств несколькими шлюзами.

Включается в `global_conf.json`:

```json
"SX130x_conf": {
    "fine_timestamp": {
        "enable": true,
        "mode": "all_sf"
    }
}
```

* `all_sf` — SF5…SF12, ниже пропускная способность приёмника;
* `high_capacity` — SF5…SF10, выше пропускная способность.

Ограничения: только LoRa BW 125 кГц; при слабом сигнале метка может не
вычислиться и поле `ftime` в конкретном кадре просто не появится. Значение
полезно лишь в паре с `tmms` — без привязки к шкале GPS это уточнение
локального счётчика, несопоставимое между шлюзами.

## Почему UART именно PL011

У Raspberry Pi 4 два UART на GPIO14/15: аппаратный PL011 (`/dev/ttyAMA0`) и
mini-UART (`/dev/ttyS0`). По умолчанию PL011 занят Bluetooth, а на пины выведен
mini-UART, тактовая частота которого привязана к частоте ядра — при
масштабировании частоты скорость обмена «плывёт» и NMEA рассыпается.

`dtoverlay=disable-bt` освобождает PL011 и выводит его на GPIO14/15, после чего
`/dev/serial0` указывает на `/dev/ttyAMA0`. Дополнительно отключается
`hciuart.service`. Альтернатива, если Bluetooth нужен, — оставить mini-UART и
зафиксировать `core_freq_min=500` (скрипт `01-system-prepare.sh` делает это
автоматически, если `GPS_TTY=/dev/ttyS0`).

Последовательная консоль ядра на том же порту читает NMEA «в себя» и мешает
форвардеру, поэтому `console=serial0,115200` удаляется из `cmdline.txt`, а
`serial-getty@*` отключается.

## Схема запуска

```
lora-pkt-fwd.service
  ExecStartPre  tools/reset_lgw.sh start   # сброс SX1303/SX1261 через GPIO
  ExecStart     packet_forwarder/lora_pkt_fwd
                  ├── читает ./global_conf.json и ./local_conf.json из WorkingDirectory
                  ├── SPI /dev/spidev0.0 — приём пакетов
                  ├── UART gps_tty_path  — NMEA
                  └── UDP → сетевой сервер (Semtech UDP protocol)
  ExecStopPost  tools/reset_lgw.sh stop
```

`local_conf.json` перекрывает одноимённые поля `global_conf.json` — скрипт
создаёт его пустым (`{}`), чтобы старые значения оттуда не удивляли.
